    Type Pack 사용하기¶

    Type Pack은 그래프가 보유할 수 있는 엔티티 종류(IP 주소, 도메인, 멀웨어 패밀리, 위협 행위자 등)를 정의하는 작은 JSON 번들입니다. 프로젝트에 설치하면 노드를 생성할 때 해당 유형을 사용할 수 있고, 캔버스에 각 노드가 어떻게 보일지 알려줍니다.

    Type Pack이 제공하는 것¶

    Type Pack은 엔티티(노드) 유형을 선언합니다. 엣지에는 유형이 없습니다: 각 엣지는 자유 텍스트 라벨을 가지며, 이 라벨은 사용자가 엣지를 그릴 때 입력하거나 연결을 찾아낸 플러그인이 씁니다. 각 엔티티 유형은 다음을 포함합니다:

    • label_property — 캔버스에서 노드 이름으로 표시되는 속성 값. IP 주소의 경우 주소 자체, 취약점의 경우 CVE ID입니다. 일부 유형은 대신 여러 속성을 조합한 라벨 (label_template)을 쓰며, 그 속성이 모두 채워지기 전까지는 label_property 값을 표시합니다.
    • 속성 세트 — 입력할 수 있는 명명된 필드(예: country_code, asn, registrar). 노드 선택 시 Properties(속성) 패널에 나타나며, 각 값은 담긴 값의 종류에 맞게 표시됩니다 (값 읽기). 속성을 편집하면 그 값이 유형이 선언한 종류, 허용 값, 패턴이나 범위에 맞는지 검사합니다(예: country_code는 대문자 두 글자, asn은 1부터 4294967295까지의 정수여야 함). 검사를 통과하지 못한 값은 저장되지 않고, 이유를 알리는 메시지가 표시됩니다. 노드는 유형이 선언하지 않은 필드도 가질 수 있습니다. 플러그인이 이런 필드를 쓰며, 사용자도 직접 더할 수 있습니다(필드 더하기와 지우기).
    • icon 및 color — 노드가 캔버스와 Types(유형) 및 Properties 패널에서 렌더링되는 방식을 결정하는 시각적 요소.

    Type Pack 설치하기¶

    다른 항목을 설치하는 것과 동일한 방식으로 Type Pack을 설치합니다(둘러보기 및 설치 참조). 설치되면 해당 유형이 Types 패널에 나타나고 노드 생성 시 선택 가능해집니다. 최소 하나의 Type Pack이 설치될 때까지 선택할 수 있는 엔티티 유형이 없습니다.

    Types 패널에서 유형은 팩이 아니라 카테고리별로 묶이므로, 한 팩이 여러 그룹을 채울 수 있습니다(Infrastructure 팩은 Infrastructure와 Web 양쪽에 나타남). 각 그룹에는 개수가 표시됩니다. 유형에 마우스를 올리면 설명과 Category:, 그리고 출처인 Type pack:이 표시됩니다. 유형을 클릭하면 해당 유형의 새 노드(New <유형> 라벨의 자리표시자)가 생성되고 바로 선택되어 속성을 채울 수 있습니다. 유형 옆의 상자는 그 유형의 노드가 캔버스에 그려지는 동안 체크되어 있고, 체크를 해제하면 그 노드들을 숨깁니다(노드와 엣지 숨기기 참조). 위쪽의 Search types… 상자는 유형 이름, 카테고리, 설명, 팩 이름으로 목록을 거릅니다. 패널이 이 상자를 담기에 너무 좁으면 유형 아이콘만 표시됩니다. 설치된 Type Pack이 없으면 패널이 그렇게 알려 주고 Browse the marketplace 버튼을 제공합니다. 로그인하지 않고 공유된 프로젝트를 보는 방문자에게는 이 버튼이 표시되지 않습니다.

    노드를 생성할 때 설치된 Type Pack에서 유형을 선택합니다. Vineyard는 해당 선택을 category.name 형식의 정규화된 문자열로 저장합니다 — 예: infrastructure.ip_address 또는 threat.malware. 플러그인은 자신이 소비하고 생성하는 것을 선언할 때 동일한 형식을 참조합니다.

    레퍼런스 팩¶

    Vineyard는 여러 공식 Type Pack을 제공합니다. 각각은 독립적입니다 — 조사에 필요한 것만 설치하세요 — 그리고 함께 사용하도록 설계되어 있습니다: 엣지 하나가 서로 다른 팩의 노드를 연결할 수 있습니다(threat.malware가 infrastructure.ip_address와 통신하는, cryptocurrency.crypto_address가 identity.person에 의해 제어되는 등).

    팩 (identifier) 카테고리 유형 모델링 대상
    Infrastructure (…typepacks.infrastructure) infrastructure, web 15 정찰 중 매핑하는 네트워크, 그리고 그 위에서 관측되는 웹 리소스(URL), 웹 지문(헤더, 파비콘, DOM 해시), 트래킹 ID 엔티티
    Threat (…typepacks.threat) threat 10 위협 인텔리전스 (STIX 정렬)
    Identity (…typepacks.identity) identity 7 사람, 조직, 온라인 페르소나
    Financial (…typepacks.financial) financial 4 거래소와 그 밖의 가상자산사업자, 은행 계좌, 옛 암호화폐 유형 두 개
    Cryptocurrency (…typepacks.cryptocurrency) cryptocurrency 4 모든 체인의 주소, 거래, 토큰, 자금을 맡지 않는 서비스. 네트워크로 식별
    Endpoint (…typepacks.endpoint) endpoint 6 호스트 / DFIR 아티팩트
    Geospatial (…typepacks.geo) geo 3 장소와 물리적 맥락
    Social Media (…typepacks.social) social 5 플랫폼에 무관한 계정, 게시물, 해시태그, 그룹, 미디어
    Telegram (…typepacks.telegram) telegram 4 가입 없이 수집한 계정, 채널, 슈퍼그룹, 게시물

    Financial — 은행 계좌¶

    계좌번호는 은행 안에서만 유일하므로 financial.bank_account는 bank_code와 account_identifier를 함께 써서 식별합니다. 두 은행의 같은 번호는 두 노드이고, 라벨에 은행 이름이 붙습니다(123456789012 · KB Kookmin). 두 값 모두 공백과 하이픈 없이 씁니다. 123-456-789012 같은 값은 거부되고, 메시지가 어떤 형식으로 써야 하는지 알려 줍니다. bank_code는 그 나라의 은행 코드가 있으면 그것(한국은 세 자리, 예: 004, 088, 090), 없으면 SWIFT/BIC입니다. 은행 이름은 쓰지 않습니다. KB나 SHINHAN 같은 값은 거부됩니다. IBAN은 은행을 이미 담고 있으므로 비워 둡니다.

    AI 에이전트는 은행 계좌를 식별하는 필드가 무엇인지와 은행 코드를 쓰는 형식을 안내받습니다. 그래도 은행 코드 없이 쓴 계좌는, 어느 은행의 계좌이든 은행 코드 없는 같은 번호의 다른 계좌와 한 노드가 됩니다. 에이전트가 만든 은행 계좌를 검토할 때 은행 코드가 들어 있는지 확인하세요.

    신고된 계좌의 상태는 따로 적는 필드가 있습니다.

    속성 기록하는 것
    fraud_registration 사기이용계좌로 등록됨(registered), 확인했으나 등록되지 않음(not_registered), 등록 후 해제됨(released)
    payment_suspended_at 계좌의 지급정지 시각
    report_channels 신고한 곳, 한 줄에 하나(112, 1332, 계좌 개설 은행…)
    status_checked_at, status_source 상태를 마지막으로 확인한 시각과 확인해 준 곳

    account_holder는 명의인입니다. 명의인은 계좌를 실제로 쓴 사람이 아닌 경우가 많습니다. 계좌를 운용한 사람은 identity.person으로 만들고 엣지로 잇습니다. AI 에이전트는 은행 계좌의 속성도 다른 노드와 똑같이 읽으므로, 에이전트가 노드를 읽으면 계좌번호와 명의인 이름이 AI 제공자로 갑니다. 사건에 이름이 필요하지 않으면 account_holder를 비워 두세요.

    Financial 2.0.0 이전에 만든 은행 계좌에는 은행 코드가 없어서, 같은 계좌를 새로 쓰면 다른 노드가 됩니다. 옛 노드에 은행 코드를 넣고 번호의 하이픈을 지우면 그 계좌의 이후 쓰기는 그 노드로 들어옵니다. 이미 따로 생긴 노드는 그대로 남습니다. 번호에 하이픈이 있는 옛 계좌에도 에이전트는 상태를 적을 수 있습니다. 편집은 바꾸는 값만 검사하기 때문입니다.

    Infrastructure — 자세히 보기¶

    run.vineyard.typepacks.infrastructure는 정찰 중 매핑하는 네트워크 측 엔티티를 infrastructure 카테고리로 모델링합니다:

    유형 (category.name) 표시 라벨 주요 속성
    infrastructure.ip_address IP 주소 version, country_code, asn, reverse_dns
    infrastructure.domain 도메인 이름 registrar, created_date, name_servers
    infrastructure.host 호스트 이름 operating_system, open_ports, hosting_provider
    infrastructure.autonomous_system ASN autonomous_system_name, registry
    infrastructure.netblock CIDR network_name, asn
    infrastructure.dns_record 이름, 유형, 값 (예: www.example.com A 93.184.216.34). 유형과 값이 채워지기 전에는 레코드 이름 record_type, record_value, ttl
    infrastructure.whois_record 주체 (도메인/IP) registrant, registrar, created_at
    infrastructure.certificate SHA-256 지문 fingerprint_sha1, subject_common_name, issuer, not_after
    infrastructure.ssh_host_key 키의 SHA-256 (16진수) key_type
    infrastructure.technologies 기술 이름 kind, vendor, version, cpe

    같은 팩이 별도의 web 카테고리로 유형 다섯 개를 더 제공합니다:

    유형 (category.name) 표시 라벨 주요 속성
    web.url URL domain (일반 텍스트로 적은 호스트 이름. 도메인 노드와는 엣지로 연결), http_status
    web.hhhash HTTP 헤더 해시 header_count, server_hint
    web.favicon_hash Shodan 방식 MMH3 해시 (부호 있는 10진수) mmh3_hex, md5, sha256, phash, dhash, favicon_url
    web.dom_hash DOM 구조 해시 tag_count
    web.tracking_id 페이지에 적힌 그대로의 식별자 (예: G-SXM8TFRYSW), 동일성은 provider + value provider, kind

    web.favicon_hash는 파비콘 하나를 검색 서비스들이 색인하는 형식별로 모두 담습니다. Shodan·FOFA· Censys·ZoomEye는 hash_value, Criminal IP는 mmh3_hex, Censys·ZoomEye·360 Quake·Hunter.how· ONYPHE·VirusTotal은 md5, Censys·Netlas·urlscan.io는 sha256으로 찾고, phash와 dhash는 비트가 몇 개 다른지로 비교하는 지각 해시입니다. AI 에이전트는 similar_hashes로 이 값을 비교하고, Shared-Attribute Clustering 팩은 phash나 dhash가 64비트 중 10비트 이하로 다른 파비콘을 similar favicon 엣지로 잇습니다(실행할 때 바꿀 수 있음). 빈 아이콘이나 한 가지 색 아이콘은 색과 관계없이 해시가 같고, 대칭인 로고의 phash는 그 값과 몇 비트밖에 다르지 않으므로, 둘 다 그 값과 같거나 가까운 해시는 비교하지 않습니다. 그 파비콘의 다른 해시는 그대로 비교합니다.

    infrastructure.certificate는 SHA-256으로 식별합니다. 출처가 SHA-1도 알려 주면(Shodan, Censys, VirusTotal) fingerprint_sha1에 함께 담습니다. abuse.ch SSLBL 같은 차단 목록은 인증서를 SHA-1로만 적고, SHA-1은 SHA-256에서 계산할 수 없기 때문입니다. abuse.ch 팩의 SSLBL Certificate Check가 이 값을 읽습니다(abuse.ch로 악성코드 조회하기 참조).

    infrastructure.domain은 Infrastructure 4.3.0부터 .한국(xn--3e0b707e)이나 .рф(xn--p1ai) 같은 국제화 최상위 도메인 아래의 이름도 받습니다. 유니코드(사이트.한국)로 적어도, 퓨니코드 (xn--vf4b27jhrk.xn--3e0b707e)로 적어도 같은 도메인입니다. 4.3.1부터는 이름의 나머지 부분처럼 퓨니코드 접두사도 대문자로 적을 수 있습니다(EXAMPLE.XN--P1AI). AI 에이전트의 extract_indicators는 텍스트에서 읽은 이름을 퓨니코드로 적습니다. 이전 버전의 프로젝트는 팩을 업데이트하기 전까지(마켓플레이스에서 카드의 Update) 이런 이름을 거부합니다.

    각 유형은 자체 아이콘과 색상을 제공합니다.

    Endpoint — 호스트 아티팩트¶

    run.vineyard.typepacks.endpoint는 침해 사고 대응자가 단말에서 찾은 것을 담습니다. 이 팩은 Host Artifacts 플러그인 팩이 이미 가진 내보내기로 채웁니다. 그 팩의 Process Activity Import 플러그인은 Run plugins 패널에서 고른 파일(JSON, JSON lines, CSV, Windows 이벤트 XML. 기기 안에서 파싱)에서 Sysmon 이벤트 1·3·22나 ECS 프로세스·네트워크·DNS 이벤트를 읽고, 다음 링크를 그립니다:

    From → to 라벨 엣지 데이터
    endpoint.process → endpoint.process spawned 없음
    endpoint.process → endpoint.file executed from 없음
    endpoint.process → infrastructure.ip_address connected to. 모든 연결이 인바운드였으면 accepted connection from source, events, direction, first_seen, last_seen, ports, port_count, protocols, remote_hostnames
    endpoint.process → infrastructure.domain queried source, events, first_seen, last_seen, answers, failed_events, statuses

    프로세스는 프로세스 GUID, 이미지 이름, PID로 식별되므로 Sysmon ProcessGuid나 ECS process.entity_id가 없는 레코드는 건너뜁니다. 이것이 없으면 두 호스트의 같은 이름·PID가 노드 하나가 됩니다. 프로세스 유형에는 호스트 필드가 없어서, 플러그인은 컴퓨터 이름을 별도 필드 hostname에 적고 Properties 패널이 이를 보여 줍니다. 한 프로세스와 한 목적지 사이의 이벤트는 모두 링크 하나가 되고, 그 events는 레코드 수가 아니라 연결이나 질의의 수입니다. Elastic Defend는 연결이 열릴 때와 닫힐 때 한 번씩 기록하지만 이벤트는 하나입니다. 새 링크는 처음 가져올 때부터 이 요약을 담습니다. 나중의 내보내기를 가져오면 그 요약은 더해지지 않고 바뀌며, 나중의 내보내기에 값이 없는 키는 비워집니다. 검토 목록에는 요약이 바뀐 링크만 나오므로, 같은 내보내기를 다시 가져오면 아무것도 스테이징되지 않습니다. 프로젝트에 이미 있는 링크는 직접 바꾼 라벨을 포함해 라벨을 그대로 두고 요약만 씁니다. 라벨을 바꾼 spawned나 executed from 링크는 건드리지 않습니다. 노드 하나에 담을 수 없을 만큼 긴 명령줄(Linux는 수 MB의 인자를 허용)은 앞부분만 남기고 자르며, 노드의 command_line_truncated와 command_line_length에 그 사실을 적습니다. 루프백과 링크 로컬 트래픽은 가져오지 않고, 사설망 주소와 내부 이름은 그 옵션을 켰을 때만 가져옵니다. update.example.xn--p1ai처럼 국제화 최상위 도메인 아래 이름의 DNS 조회는 그 Domain으로 가는 queried 링크가 됩니다. 아직 Infrastructure 4.2인 프로젝트는 그런 이름을 받지 않으며, 요약은 그것을 어떤 Domain 유형도 받지 않는 이름과 함께 세고(… names this project's Domain type does not accept (Infrastructure 4.3 or later takes internationalised names)) 쓰기 실패로 치지 않습니다.

    서버에 남는 호스트 데이터

    호스트 이름, 사용자 이름, 명령줄은 노드 필드가 됩니다. Vineyard 서버의 프로젝트에서는 그 서버에 저장됩니다. 호스트 데이터가 이 컴퓨터 밖으로 나가면 안 되는 사건이라면 데스크탑 앱의 로컬 모드를 쓰세요(로그인 모드와 로컬 모드).

    다른 팩도 같은 형태를 따릅니다 — 예를 들어 Threat 팩은 threat.malware, threat.threat_actor, threat.indicator, threat.operation(캠페인 내의 경계된 작업 — 하나의 캠페인은 여러 개의 operation을 포함할 수 있음)을, Identity 팩은 활동 뒤의 사람과 페르소나를 추가합니다.

    Cryptocurrency — 자세히 보기¶

    run.vineyard.typepacks.cryptocurrency는 cryptocurrency 카테고리의 유형 한 벌로 모든 체인을 다루고, 어느 체인인지는 network로 나타냅니다. 같은 문자열도 네트워크가 다르면 다른 계정이므로 (Bitcoin과 Bitcoin Cash의 1… 주소, Ethereum과 BSC의 같은 0x… 주소) network는 식별 값의 일부이고, 그런 두 노드는 병합되지 않습니다.

    유형 (category.name) 표시 라벨 식별 주요 속성
    cryptocurrency.crypto_address 주소와 네트워크 network + address + memo address_kind, balance, first_funder, public_label, sanctioned
    cryptocurrency.crypto_transaction 해시와 네트워크 network + tx_hash block_height, block_time, status, fee
    cryptocurrency.crypto_token 심볼과 네트워크 network + contract_address standard, decimals, issuer
    cryptocurrency.crypto_service 이름 name service_type (mixer, bridge, gambling, merchant, defi)
    • 대소문자. hex, bech32, CashAddr, TON raw 값은 대소문자와 관계없이 일치합니다. 그래서 EIP-55 체크섬 표기 주소와 소문자 표기는 한 노드이고, hex 64자 해시는 0x 유무와 관계없이 일치합니다. Base58 값(비트코인 레거시, TRON, Solana, Monero, XRPL)은 적힌 그대로 비교합니다.
    • evm과 unknown은 아직 정해지지 않은 네트워크입니다. 출처가 체인을 말하지 않은 0x… 주소, 그리고 출처도 형식도 네트워크를 정하지 못한 그 밖의 주소입니다. 이 노드는 따로 남고, 네트워크가 정해지면 evm·unknown 노드에서 그 네트워크의 노드로 same address on을 긋습니다.
    • 거래소와 고객 자금을 맡는 그 밖의 서비스(OTC 데스크, 수탁형 지갑, 결제대행)는 financial.exchange입니다. crypto_service는 자금을 맡지 않는 서비스에 씁니다.
    • 금액(balance, fee)은 네트워크 기본 단위의 10진 문자열입니다. 정밀도는 그대로지만 숫자로 정렬되지 않습니다.
    • Financial 팩의 crypto_address와 crypto_transaction은 기존 노드를 위해 남아 있고 "(legacy)"로 표시됩니다. 새 유형과 병합되지 않습니다. 두 팩을 함께 설치하면 짧은 이름 crypto_address는 Cryptocurrency 팩의 유형을 가리킵니다.

    network 값 대부분에는 다른 도구와 주고받는 CAIP-2 체인 ID가 있습니다. 초안이나 제안 단계인 것도 있고, 등재된 ID가 없는 것도 몇 있습니다. 이 ID는 식별 값에 들어가지 않으므로, 나중에 고쳐도 노드가 갈라지지 않습니다.

    시작 → 끝 라벨 데이터
    주소 → 주소 sent to network, 출처별 summary_<출처>(asset, symbol, count, total, first, last, window_from, window_to, complete), 최근 20건 recent(tx_hash, asset, amount, time), first_funding, deployment

    sanctioned, sanctions_programs, sanctions_as_of는 sanctions_as_of 날짜의 목록에 대한 스크리닝 결과입니다. false는 그 목록에 없다는 뜻이지, 문제가 없다는 뜻이 아닙니다. Sanctions Screening 플러그인 팩이 OFAC SDN 목록으로 이 값을 쓰고, 어느 목록인지 sanctions_list에 적고, listed address 링크를 그립니다. 다른 목록이나 분석가가 이미 sanctioned로 표시한 주소는 건드리지 않습니다. 제재 목록 스크리닝을 참조하세요.

    Chain Explorer 플러그인팩은 계정이나 키 없이 이 유형들을 채웁니다. 주소의 거래 이력과 상대 주소, 거래의 입력과 출력, TRON과 XRP Ledger의 첫 자금 공급자, 계약 배포자와 토큰, 탐색기 라벨, USDT·USDC 동결 여부를 읽습니다. Identify Crypto Network 플러그인은 evm이나 unknown 주소, 옛 Financial 주소, 결제용 추적 ID의 네트워크를 정하고 위 표의 same address on과 same as 엣지를 그립니다. 여러 네트워크가 같은 형식을 쓰는 주소는 그 네트워크들이 모두 응답한 뒤 활동이 있는 네트워크마다 노드가 됩니다. 응답하지 않는 탐색기가 있으면 그 주소는 다음 실행에서 다시 판정합니다. 거래를 보낸 적이 없고 코인도 코드도 없는 EVM 주소는 판정하지 않은 채로 남습니다. 다루는 네트워크는 Bitcoin, Litecoin, Bitcoin Cash, Dogecoin, Dash, Zcash, Ethereum, BNB Smart Chain(최근 30일), OP Mainnet, Avalanche C-Chain, Ethereum Classic, TRON, Solana, XRP Ledger, TON입니다. Polygon, Arbitrum, Base의 이력은 키가 필요한 팩이 다룹니다.

    Blockchair 플러그인 팩이 위 표의 거래 행(input to, output to)과 same address on을 Bitcoin과 그와 같은 구조의 체인 여섯 개에서 씁니다. Blockchair로 코인 따라가기를 보세요.

    Blockscout PRO 플러그인 팩은 본인의 무료 키로 Ethereum, OP Mainnet, Ethereum Classic, Arbitrum One에서, 유료 Blockscout 플랜으로는 Polygon PoS와 Base에서도 이 유형과 링크를 채웁니다. Blockscout PRO로 자금 추적하기를 보세요.

    Helius로 보는 Solana. Helius 플러그인팩에는 Helius API 키가 필요하고, 무료 플랜으로 이력과 첫 자금 공급자를 볼 수 있습니다. Solana 지갑은 SPL 토큰을 자기가 소유한 토큰 계정에 두므로, 일반 Solana RPC의 지갑 이력에는 그 지갑으로 들어온 USDC 송금이 빠집니다. 이 팩의 이력은 그 토큰 계정의 잔액을 바꾼 거래까지 읽습니다. summary_helius와 recent가 담긴 sent to 링크를 씁니다. recent는 최근 이체 20건이며, 링크에 이미 있는 목록에 합쳐 넣습니다. 지갑이 SOL을 자기 wSOL 계정으로 감싼(wrap) 것은 지불로 세지 않습니다. 주소에는 balance, last_seen, history_examined, history_complete를 쓰고, first_seen은 이력을 끝까지 읽었을 때만 씁니다. 첫 자금 공급자 플러그인은 first_funder, first_funding_tx, activated_at을 쓰고, 공급자에서 주소로 가는 sent to 링크에 first_funding을 더합니다. 그 키의 source가 찾은 방법입니다. helius funded-by는 Helius의 자체 조회로 유료 플랜(Developer 이상)이 필요합니다. helius earliest SOL deposit은 주소의 잔액이 처음 0에서 늘어난 거래에 있는 SOL 송금으로, funded-by도 같은 정의를 씁니다. 무료 키로는 이 방법을 쓰고, funded-by에 기록이 없는 주소도 이 방법으로 찾습니다. 송금이 아니라 프로그램이 처음 SOL을 넣어 준 주소에는 공급자를 쓰지 않습니다. Helius의 신원 라벨(public_label, helius_category, 거래소·서비스·회사로 가는 attributed to)도 유료 플랜이 필요합니다. 2022년 12월 이전의 토큰 전송은 토큰 계정으로 찾지 못합니다.

    여러 홉에 걸쳐 자금을 따라가려면 Crypto fund-flow tracing Skill Pack이 에이전트에게 이 플러그인들을 쓰는 법을 알려 줍니다. 홉 전에 주소마다 네트워크를 정하고, 자산·시각· 금액으로 전송을 따라가고, 거래소와 서비스에서 멈추고, 자금이 닿은 거래소와 스테이블코인 발행사에 보낼 동결·자료 요청을 정리합니다. 전송은 플러그인이 그은 엣지로 남고, 에이전트가 라벨이나 입금 패턴으로 추정한 주인은 그래프가 아니라 보고서에 후보로 씁니다.

    Type Pack 혼합하기

    필요한 만큼 Type Pack을 설치하세요 — 하나의 정규화된 유형 네임스페이스를 공유하며 설계상 상호 연결됩니다. threat.malware를 그것이 비콘하는 infrastructure.ip_address에 연결하고, threat.campaign을 identity.organization에 귀속시키고, 몸값 cryptocurrency.crypto_transaction을 추적할 수 있습니다.

    신원 및 중복 제거

    플러그인이나 AI 작업이 노드를 추가할 때, Vineyard는 유형 + 유형의 식별 필드로 중복을 제거합니다 — 유형이 identity_properties를 선언하면 그 필드들(예: identity.account → username + platform, endpoint.file → SHA-256·파일 이름·경로·호스트, endpoint.process → 프로세스 GUID·이름·PID, financial.bank_account → 은행 코드·계좌번호), 아니면 label_property 값입니다. 같은 유형과 같은 식별 값의 두 노드는 병합되고 속성이 결합됩니다. 팩이 대소문자 무시로 표시한 필드(도메인, 호스트 이름, 이메일, 핸들 등)는 대소문자와 관계없이 일치합니다. 암호화폐 주소와 거래 해시는 hex·bech32 표기의 대소문자와 관계없이 일치하지만, Base58 주소는 적힌 그대로 비교하고 네트워크도 식별 값의 일부입니다. Infrastructure 4.3.0부터 도메인·호스트·DNS 레코드 이름은 끝의 점과 관계없이 퓨니코드 표기로, IP 주소는 표준 표기(IPv6는 RFC 5952 형식)로, URL은 스킴·호스트의 대소문자나 기본 포트, 퍼센트 인코딩을 어떻게 썼든 일치합니다. URL 경로의 대소문자는 그대로 비교합니다. 노드는 이미 가진 표기를 유지합니다. 다른 표기로 같은 값을 쓰면 다른 필드만 더해지고 식별 값은 그대로 남습니다. 따라서 가장 유용한 라벨은 읽기 쉽고 식별적인 것입니다. 대부분의 유형은 자연적으로 고유한 필드(IP, CVE ID, 트랜잭션 해시, WHOIS 주체)를 키로 사용합니다. 라벨이 본질적으로 고유하지 않은 유형(identity.person의 이름, identity.organization의 이름)은 같은 라벨을 공유하는 서로 다른 엔티티가 병합되므로, 구분되는 라벨 (예: John Smith (DOB 1990))을 주세요. 이 두 유형은 라벨만으로 식별되므로 생년월일이나 등록번호 같은 다른 속성을 채워도 서로 구분되지 않습니다. 전화번호는 적힌 그대로 식별하므로 +82 10-1234-5678과 010-1234-5678은 서로 다른 identity.phone_number 노드입니다. Phone Numbers 플러그인팩이 둘이 공유하는 E.164 표기를 e164에 쓰고(Identity 2.4.0 이상), region과 번호 대역으로 추정한 line_type도 채웁니다. 라벨은 바꾸지 않습니다. e164가 같은 노드는 중복으로 찾아집니다(Identity 2.5.0 이상). 수동으로 추가한 노드는 절대 자동 병합되지 않습니다. 같은 엔터티인데 프로젝트에 이미 두 노드로 있는 것은 AI 에이전트의 find_duplicates와 merge_nodes가 검토를 거쳐 찾아 합치거나(중복과 병합 참고), 직접 합칩니다(노드 병합 참고).

    Properties 패널에서¶

    노드를 선택하면 Properties 패널에 필드가 나옵니다. 패널이 그 필드에 대해 말할 수 있는 것의 많은 부분은 노드의 Type Pack이 정합니다.

    • 유형이 선언한 필드가 팩에 적힌 순서대로 먼저 나오고, 필수 필드에는 *가 붙습니다. 노드가 가졌지만 유형이 선언하지 않은 필드는 그 뒤 Added fields 아래에 나옵니다.
    • 선언된 필드는 값이 맞는 한 유형에 맞는 방식으로 편집합니다. 나열된 값 가운데 고르는 목록, 참·거짓 스위치, 날짜 선택기, 숫자 입력칸입니다(값 편집하기).
    • 바꾼 값은 저장하기 전에 선언된 유형, 허용 값, 패턴이나 범위로 검사합니다(저장과 검사). 추가된 필드는 검사하지 않습니다.

    노드의 Type Pack이 설치되지 않았거나 불러오지 못했어도 패널은 노드가 가진 필드를 모두 보여 주지만, 어떤 필드도 필수로 표시하지 않고 어떤 값도 검사하지 않습니다.

    버전¶

    Type Pack은 시맨틱 버저닝을 사용합니다. MAJOR 버전 증가는 유형 정의의 파괴적 변경을 의미합니다 — 예: 유형 이름 변경 또는 제거 — 기존 유형을 사용하는 노드를 수정해야 할 수 있습니다. 마이너 및 패치 업데이트(새 선택적 속성, 시각적 조정)는 기존 노드를 깨지 않습니다.
