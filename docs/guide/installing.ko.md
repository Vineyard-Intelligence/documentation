# Plugin Pack 및 Type Pack 둘러보기 및 설치

이 페이지에서는 마켓플레이스 둘러보기와 **설치**를 클릭할 때 실행되는 클라이언트 측 설치 파이프라인을 다룹니다.

## 마켓플레이스 둘러보기

마켓플레이스는 완전히 정적인 카탈로그입니다: 모든 Plugin Pack과 Type Pack이 하나의 메타데이터 파일에 있으며, 모든 검색, 필터링, 정렬은 브라우저에서 수행됩니다. 계정, 서버 쿼리, 텔레메트리가 없습니다.

동일한 컴포넌트와 데이터를 공유하는 두 곳에서 둘러볼 수 있습니다:

- **이 사이트의 [마켓플레이스 페이지](../marketplace.md)** — 공개 읽기 전용 브라우저.
- **Vineyard 앱 내부의 인앱 미러** — 동일한 카드 그리드와 상세 보기로, **설치**가 즉시 설치 파이프라인으로 전달될 수 있도록 직접 콜백과 연결됩니다.

### 검색

검색 상자는 항목의 **이름**, **작성자**, **설명**과 일치합니다. 조각을 입력하면 그리드가 입력에 따라 실시간으로 필터링됩니다 — 제출할 필요가 없습니다. 예를 들어 `roulette`을 검색하면 Chaos 팩이, `cidr`을 검색하면 CIDR Expand가 표시됩니다.

### 필터링

세 가지 측면이 그리드를 좁히며, 이들은 조합됩니다:

| 측면 | 역할 |
|---|---|
| **유형** | 세그먼트 토글: **전체**, **Plugin Pack**, **Type Pack**. |
| **카테고리** | Type Pack 카테고리의 드롭다운 (예: `infrastructure`, `threat`). Type Pack이 보기에 있을 때 표시되며, 해당 카테고리를 선언한 항목이 일치합니다. |
| **인증만** | 작성자가 인증 목록에 없는 모든 항목을 숨기는 체크박스. |

### 정렬

**정렬** 드롭다운이 보이는 카드를 재정렬합니다:

- **이름 A→Z** (기본값) 및 **이름 Z→A**
- **인증 우선** — 인증된 작성자가 상단에 표시된 후 알파벳 순
- **유형별 그룹** — Plugin Pack끼리, Type Pack끼리, 각 그룹 내 알파벳 순

### 카드 읽기

각 카드는 간결한 요약입니다:

- **아이콘** 및 **이름**.
- **작성자**, 작성자가 인증된 경우 **인증 표시**(✓)가 뒤따릅니다.
- 한 줄 **설명**.
- 푸터의 **배지**, 유형에 따라 다름:
    - **Plugin Pack**의 경우: 지원 플랫폼별 **플랫폼** 배지 하나 (예: `web`), 권한 요약 — 선언된 엔드포인트를 호출하는 경우 `network`, 그래프를 수정할 수 있는 경우 `graph write`.
    - **Type Pack**의 경우: `schema only` 배지 (Type Pack은 코드를 포함하지 않으며 스코프를 요청하지 않음), 엔티티 유형 및 엣지 유형 수와 같은 개수.

### 상세 보기

카드를 클릭하면 전체 정보가 담긴 상세 드로어가 열립니다.

**권한.** 플러그인의 경우, **권한** 패널이 요청된 각 스코프를 스코프 문자열과 기능 요약에서 파생된 문장으로 다시 표현합니다. 예:

- `node:read` + `node:delete` + `edge:delete` → *"그래프: 이 프로젝트의 노드/엣지를 읽고 삭제합니다."*
- `network` 스코프 → *"네트워크: 선언된 외부 엔드포인트를 호출합니다."*
- `publish` 기능 → *"게시: 프로젝트에 메시지를 게시할 수 있습니다."*
- `config` 요구사항 → *"설정: 설치 시 설정 값이 필요합니다."*

전체 어휘(`node:read`, `edge:delete`, `message:post` 등)는 [스코프](../reference/scopes.md)를 참조하세요.

**유형 흐름: consumes → produces.** 플러그인이 입력 또는 출력을 선언한 경우, 드로어는 데이터 흐름을 설명하는 **유형 칩**을 표시하며, 각각 `category.name` 형식을 사용합니다 — 예: `consumes · infrastructure.ip_address` 및 `produces · infrastructure.cidr_block`. 이를 통해 플러그인이 어떤 [Type Pack](typepacks.md)이 먼저 설치되어야 하는지 알 수 있습니다.

**신원 정보.** 사이드바가 안정적인 항목 정보를 나열하며, 식별자에 복사 버튼이 있습니다:

- **식별자** — 역DNS ID, 예: `run.vineyard.plugins.cidr_expand` (Type Pack은 `run.vineyard.typepacks.*` 사용).
- **버전**, **라이선스**, **플랫폼** (플러그인의 경우).
- **저장소** 및 **Ref** — 작성자의 저장소와 설치 시 번들을 가져오는 불변 고정 ref (`repo@ref`).

**유형 팔레트 (Type Pack).** Type Pack의 상세 보기는 권한 패널을 **유형 팔레트**로 대체합니다 — 팩이 제공하는 엔티티 및 엣지 유형 — 카테고리와 개수와 함께. Type Pack은 스키마 전용이므로 승인할 스코프가 없습니다. [Type Pack](typepacks.md)을 참조하세요.

### "인증됨"의 의미

인증 ✓는 **자체 주장되지 않습니다**. 항목은 작성자가 레지스트리의 `verified-authors.json` 목록에 등재된 경우에만 표시를 받으며, 이는 Vineyard 레지스트리가 유지 관리하며 제출자가 아닙니다. 플러그인 작성자는 자신의 `verified` 플래그를 true로 설정할 수 없습니다. 인증은 *작성자의 신원*을 증명하는 것이지, 특정 플러그인의 안전성이나 품질을 증명하는 것이 아닙니다 — 설치 전에 권한을 검토해야 합니다.

## 설치 파이프라인 (앱 측)

카드에서 **설치**를 클릭하면, 정적 페이지는 자체적으로 아무것도 다운로드하거나 실행하지 않습니다 — *레퍼런스*를 생성하여 앱에 전달하며, 앱은 매번 동일한 파이프라인을 실행합니다:

1. **항목 확인.** 간소한 레지스트리 항목 읽기 (식별자, 저장소, 불변 `ref`, 경로, 버전).
2. **전체 매니페스트 가져오기** `repo@ref/path`의 작성자 저장소에서 — 비정규화된 카탈로그 복사본이 아닌 완전한
   [`vineyard:plugin`](../reference/plugin-schema.md) 또는
   [`vineyard:typepack`](../reference/typepack-schema.md) JSON.
3. **번들 가져오기** 매니페스트의 `distribution.kind`에 따라 GitHub 릴리스에서:
   `zip` (릴리스 아카이브), `git` (저장소 트리의 파일), 또는 `inline` (매니페스트에
   번들됨).
4. **선택적 무결성 검사.** 매니페스트가 `distribution.integrity`
   (`{ algo: "sha256", hash: ... }`)를 선언한 경우, 앱이 다운로드된 바이트를 이에 대해 검증합니다.
   설치 시 force-push를 감지합니다.
5. **바이트 캐시 — 클라이언트 측 전용.** 웹에서는 **IndexedDB**, 데스크톱에서는
   로컬 파일시스템입니다. 어떤 시점에도 서버 측 콘텐츠 복사본이 없습니다.
6. **스코프 승인 대화상자.** 플러그인의 경우, 앱이 요청된
   [스코프](../reference/scopes.md)를 평이한 언어로 표시합니다(웹 미리보기에서 본 것과 동일한 `scopeToBadge()` 매핑).
   예: `node:read`, `node:delete`, `edge:delete`, `message:post`. 여기서
   승인하거나 취소합니다.
7. **활성화.** 플러그인을 실행할 수 있게 됩니다.

설치는 플러그인을 *보유하고 있음*을 기록합니다([설치 기록](#설치-기록-및-제거) 참조). 그러나 작업은 **기본적으로 임시**입니다 — 플러그인을 실행해도 서버에 아무것도 기록되지 않으며, 임시 채팅과 같습니다. [플러그인 실행하기](running-plugins.md) 및 [작업](tasks.md)을 참조하세요.

## 세 가지 설치 브리지

정적 페이지는 파이프라인을 자체적으로 실행할 수 없으므로, 세 가지 브리지 중 하나를 통해 앱에 레퍼런스를 전달합니다:

=== "딥 링크"

    ```text
    vineyard://install?manifest=<url>&type=pluginpack&ref=<ref>
    ```

    `vineyard://` 딥 링크 (상세 보기를 여는 `vineyard://show-plugin?id=...`도 있습니다).
    이는 **데스크톱에서 안정적**입니다. 공개 웹 페이지에서는 핸들러가 등록되지 않을 수
    있으므로 URL 복사 폴백이 존재합니다.

=== "설치 URL 복사"

    앱에 붙여넣을 레퍼런스를 제공하는 **"설치 URL 복사"** 버튼. 이는
    `vineyard://` 핸들러가 보장되지 않는 **웹** 페이지에서 신뢰할 수 있는 경로입니다.

=== "인앱 미러"

    **앱 내부**에서 렌더링된 동일한 둘러보기/상세 UI로, **설치**가 파이프라인으로의 직접
    콜백입니다 — 프로토콜 핸들러 없음, 복사-붙여넣기 없음.

## Type Pack 설치하기

Type Pack ([`vineyard:typepack`](typepacks.md))은 순수 JSON입니다 — 노드와 엣지
**유형**을 정의하며 실행 가능한 것은 없습니다. 설치는 동일한 가져오기-및-캐시 흐름이지만 두 가지
차이점이 있습니다:

- **스코프 없음.** Type Pack은 권한을 요청하지 않으므로 **스코프 승인 대화상자가 없습니다** —
  마켓플레이스 카드는 권한 요약 대신 "schema only"를 표시합니다.
- **활성화 = 스키마 전용.** Type Pack을 활성화하면 정규화된 유형이 캔버스와
  플러그인 `io`에서 사용 가능해집니다. 유형은 `category.name`
  (예: `infrastructure.ip_address`, `threat.indicator`)으로 참조됩니다.

!!! tip "플러그인이 Type Pack에 의존할 수 있습니다"
    `io.consumes`/`produces`가 Type Pack의 유형을 참조하는 플러그인은 해당 Type Pack이
    먼저 활성화되어야 합니다. 마켓플레이스는 의존성이 누락된 경우 **미해결 Type Pack** 상태
    ("Type Pack을 먼저 설치하세요")를 표시합니다. [Type Pack](typepacks.md)을 참조하세요.

## 설치 기록 및 제거

설치는 프로젝트별 / 사용자별 **설치 기록**으로 추적됩니다:

```jsonc
{ "identifier": "run.vineyard.plugins.korean_roulette", "version": "1.0.0", "ref": "9f1c2ad7...e6f7" }
```

이 기록(식별자, 버전, ref)을 앱이 레지스트리와 비교하여
[업데이트](../develop/updates.md)를 제공합니다. 검증된 번들은 클라이언트 측 캐시에 유지됩니다. 제거 /
삭제는 설치 기록과 캐시된 바이트를 삭제하며 — 실행이 절대 지속되지 않으므로
정리할 실행 기록이 없습니다.

## 웹 CORS 주의사항

웹에서는 **브라우저**가 GitHub에서 직접 번들을 가져옵니다. GitHub 릴리스 자산은
현재 CORS-open이므로 작동합니다. 그러나 플러그인의 번들이 CORS-open이 **아닌**
곳에서 호스팅되는 경우, 웹 설치는 실패합니다 — **버그가 아닌 의도된 설계**입니다.

!!! warning "데스크톱 폴백 사용 가능"
    CORS가 아닌 번들 호스트에 대한 의도된 해결책은 "데스크톱 앱 사용"으로, CORS 제한 없이
    앱 자체 격리 환경에서 실행됩니다. **데스크톱 Electron 셸은 현재 제공됩니다**
    (`platforms.desktop.runtime: "sandbox-js"`). 웹과 데스크톱 모두 제공 중인 런타임이며,
    `native`/`subprocess` 데스크톱 런타임은 미래 지향적 설계로 남아 있습니다.
